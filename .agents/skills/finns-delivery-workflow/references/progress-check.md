# Plane 开发计划适配与进度检查

本协议是可移植的流程核心，FINNS 的授权、技术栈和阶段要求仍由项目入口规定。其他项目复用时只迁移本协议和检查脚本，配置自己的阶段、证据和路径，不复制 FINNS 的账号、对象 ID 或批准记录。

## 每轮必须执行

接手任务、用户说“继续”、准备进入下一阶段、范围或证据变化及交付前，运行 `python -X utf8 <skill目录>/scripts/check_progress.py --root <项目根> --state <进度文件>`。FINNS 使用 `docs/delivery-progress.json`。仅普通问答不运行。先更新本轮真实证据，再复查；不能为得到通过结果而补写不存在的批准。

1. 核对用户本轮意图、任务与目标版本；没有状态文件时从现有决定/验收记录建立，未知项保留 pending，不猜测完成率。
2. 检查器逐功能读取有序门禁，验证已通过项的证据路径和 SHA-256；取第一个未满足项。缺证据、证据变化或格式错误均停止依赖它的动作。
3. AI 必须阅读证据对应段落，核对确认对象、修订、范围及实际结果。哈希只能发现文件变化，不能证明语义真实；禁止靠关键词、文件存在、口头“做过”或 Plane Done 推定通过。
4. 向用户给出：`目标版本/功能 → 当前阶段 → 依据 → 缺少什么 → AI 下一步 → 用户需做什么`。每次只突出当前关键动作。无用户决策时写“无需操作，AI 继续…”，不要请求内部设计/检查的重复批准。
5. 用户已确认且仍覆盖当前修订的决定直接复用。等待用户时继续独立且已授权的资料准备，不执行被阻断动作。

检查器是每轮调用的本地只读工具，不是后台监控，不读取聊天、不调用 MCP、不自动批准或写远程。退出码 0=所登记门禁均满足；2=存在待办/证据失效；1=配置错误。均不能单独解释为业务已上线。

## Plane 与本地的分工

| 对象 | 规则 |
| --- | --- |
| Project | 一个真实产品/项目，登记唯一 ID，需求直接归属它 |
| Cycle | 迭代容器；个人项目可按目标版本组织，无日期明确为待排期；空容器不代表需求已同步 |
| 工作项 | 一个可验收交付结果；复杂功能再拆子任务，不机械按每个阶段建卡 |
| Module | 可选的长期能力分组，不能与版本/阶段混淆 |
| Release | 可选的发布集合，实际发布与任务完成分别记录 |

每项记录：稳定 ID、产品版本、问题/范围/排除项、验收、负责人或待分配、当前阶段、依赖、证据路径、Plane 对象 ID 与最后核对时间。仓库文件作为证据入口，Plane 为管理状态权威，冲突需报告及核对，不能双向自动覆盖。

状态映射是建议，不是假定远程已有同名状态：已记录/待用户确认→Backlog；待实施→Unstarted；实施中/已实施→Started；验收通过→Completed；暂缓保留状态并注明原因。必须读取项目真实 state ID 后才能提出更新。阶段 G0–G9 独立写在正文或已有字段；不自动创建字段/状态。

G1→G2 检查点逐功能记录，只有对应工作项完成同步回读、核对无变化或明确延期才满足；项目/Cycle 创建不能替代。创建工作项、关联 Cycle、更新状态是独立写操作，遵守 [Plane 协议](plane-sync.md)。无本轮读取授权时，只使用带日期的本地回执并提示待核对。

## 状态文件契约

JSON `schema_version:1`，含 `project`、`required_gates`（有序必需门禁）、`tasks`。每个 task 含唯一 `id`、`version`、有序 `gates`；FINNS 业务任务完整列出 G0、G1、PLANE、G2…G9，不删除未来阶段来制造完成。

每个 gate：`id`、`status`（pending/pass/na）、`next_action`（AI 的具体下一步）、`user_action`（用户具体决定或无需操作）、可选 `reason`、`evidence`。证据为 `{path, sha256}`，路径相对项目根。pass 必须有证据；na 必须有理由及依据证据，由 AI 核对适用性。pending 可引用背景证据但不推定通过。批准来源写入对应决定文件并绑定修订，不能把脚本运行本身作为批准。

变更只使受影响阶段及依赖结果失效；文件哈希变化先检查是否仅新增历史记录，确认原证据仍有效才更新哈希并记录理由。代码/测试证据还需在记录中绑定源码修订或工作树快照，防止旧测试支撑新代码。完整功能状态与本轮文档任务状态分开。
