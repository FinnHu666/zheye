# 开发阶段门禁

## 门禁怎样执行

每个门禁记录：输入证据及修订、检查结果、未决项、下一步。结果只用 `通过 / 未满足 / 不适用`；不适用必须注明范围与理由，不能用“快速迭代”代替缺失证据。

用户确认与内部检查分开：需求方向、具体产品原型/范围、重大变更和发布需要对应用户授权；概设/详设完备、构建/测试结果由 AI 按已授权范围执行和检查，不额外要求用户逐份批准技术文件。Plane 写入另按逐项确认规则。

**G1→G2 增加明确的管理同步检查点**：需求评审通过后，先主动提出 Plane 差异/授权与逐项确认，处理为已同步并回读、核对无变化或用户明确延期，再开始实际产品原型制作。规则见 [Plane 同步节点](plane-sync.md)。产品评审通过不授权写入；准备原型任务书不等于原型已制作；没有回复不等于允许延期。G1 的通过状态不因等待管理同步而撤销。

| 阶段 | 必需输入与产物 | 进入下一步的条件 | 未满足时 |
| --- | --- | --- | --- |
| G0 登记 | 用户意图、稳定 ID、当前事实、目标版本、范围/排除项、验收及待决；核对历史实现 | 能清楚区分本轮授权、建议与未决 | 只补充已授权的规划，不猜范围 |
| G1 需求评审 | 分点功能、异常/兼容边界、可观察验收；决定记录标明用户确认来源和修订 | 用户确认本轮需求；转换到实际原型前完成 Plane 同步检查点或记录明确延期 | G1 通过时主动提出同步确认，不把写入授权缺失变成静默不处理 |
| G2 产品原型 | 同步检查点处理结果；可查看页面，交互需可点击；主路径及相关空/加载/错误/返回状态、演示标识、视口适配 | 用户明确确认具体原型版本与范围；反馈已落实或列出获准延期项 | 不开始对应的新业务功能开发；只有任务书时标记待制作 |
| G3 概要设计 | 组件/状态与职责、路由、权限、数据流、兼容、风险与回退取舍；关联已确认需求/原型；**设计评审记录**（见下） | 影响设计的决定明确，方案能支撑验收；复用现有栈；评审结论为通过，或带条件通过且条件已逐条关闭 | 修正设计；评审退回则回 G3 修订；重大产品变化回 G1/G2 |
| G4 详设与契约 | DTO/版本/容量/错误、身份/CSRF、幂等/并发、数据迁移/恢复（相关时）；需求到测试映射 | 实施授权覆盖本次范围，关键契约可验证，无阻断待决 | 不用代码试错偷偷决定权限或持久化边界 |
| G5 实施 | 按小闭环实现；记录最终文件范围、设计偏差、回归风险 | 行为符合确认范围，必要静态/构建检查通过 | 修复；范围变化走变更单 |
| G6 测试 | 对应验收的自动化/集成/浏览器证据、真实退出码、版本/环境、失败及未验项 | 交付必需检查通过；实测与模拟清楚区分 | 缺工具/Key 等列未验项，不能用模拟替代真实验收 |
| G7 验收 | 逐项验收表、证据、限制；真人/外部依赖项目单列 | 本轮完成条件满足；未通过不得改为“验收通过” | 保留输入/数据，修复或取得明确延期决定 |
| G8 发布 | 用户指定环境授权、发布包、四处版本、变更日志；涉及真实数据时有可恢复备份和恢复演练；回退步骤 | 授权及必要准备齐备；部署后检查实际服务版本/关键流程 | 不提前部署；失败按已准备回退，记录实际结果 |
| G9 交接 | 最终索引、决定、验证、运行环境、未验项/下一步；用户要求时同步 Plane 并回读 | 下一位 AI 不读聊天也能核对并继续 | 补齐资料，不以最后一句“完成”替代 |

**G3 设计评审轮**：概设定稿后做一轮专门判断“设计是否合理”的评审，规则、维度、独立性要求和记录格式见 [设计评审](design-review.md)。需要评审的触发条件和可豁免情形在该文件里；评审结论写入 `DESIGN_REVIEW_<功能>.md`，并与概设一起登记为 G3 证据。评审里需要用户决定的事项单列上报，不替用户决定。

每阶段完成时检查进入下一阶段的条件，而不是一次记录全部“通过”。“仅规划”任务可交付 G0/G1 的产物，不需要假装 G2–G8 已执行；业务实施前仍需满足它们。

## 小修复与复用

- 纯文档/skill：做文档及行为边界检查，不连接数据库、制作无关原型或跑收费模型。
- 修复已确认行为的小缺陷：引用原需求、原型、现有接口与复现；记录为何不改变用户流程/权限/数据。原型或设计阶段可复用这些证据，不能写“用户已确认新原型”。
- 新功能、显著布局/交互、身份/持久化或外部服务变化：处理实际影响，先提供对应评审/原型/设计，不能自行按“小修复”豁免。
- 用户明确授权的实现方案若已包含完整范围、验收及可引用原型，可复用确认，不重复询问。授权和证据不能超出当时内容。

## 冻结与变更

确认基线后保留原文及修订。新增需求用变更记录写清：触发、原行为→新行为、影响的需求/原型/接口/数据/测试、版本及回退、需要的确认。只退回受影响阶段，未受影响的历史决定保持有效。

重大范围变化在相应用户确认之前不实施；常规实现细节在授权内自主决定并记录取舍。不要机械地对每次代码修改要求确认，也不能用技术细节之名增加产品范围。

## 最低追踪关系

`需求/功能 ID → 场景与验收 ID → 原型版本/页面 → 设计/接口或数据 → 实现位置 → 测试/证据 → 发布与 Plane 工作项（如有）`。

允许多个条目共用产物；必须定位到相关小节/测试场景。未产生的节点填写“待制作/未执行/不适用及理由”，禁止用占位文件冒充完成证据。

## 按风险验证

页面验证桌面/390px/768px、直达刷新/历史导航与相关失败状态；个人数据验证未登录、跨账号、会话失效及 CSRF；数据库使用隔离 PostgreSQL 验证迁移/重复启动/恢复。模型常规测试用固定响应，收费调用按明确预算，无自动重试。HTML 模块沿用独立校验与 sandbox/CSP。细节以 finns-development 和当前源码/测试脚本为准，不照搬旧命令覆盖新运行环境。
