# FINNS 交付流程与 Plane 同步

这是项目级 skill，由根 AGENTS.md 和 finns-development 引导读取；仓库中的这份文件是唯一维护源，不另建全局副本。操作前告知用户正在使用本 skill。

## 1. 识别任务及授权

1. 先读 [AGENTS.md](../../../AGENTS.md)、[finns-development](../finns-development/SKILL.md)、[下一轮计划](../../../docs/NEXT_ITERATION_PLAN.md) 和 [交接](../../../docs/AI_HANDOFF.md)，核对源码、四处版本和 Git 状态；保留原有改动。
2. 明确本轮是记录/规划、原型、实施、验收还是发布。记录不授权业务实现，实施不自动授权主站部署、Git 提交或 Plane 写入。
3. 以明确产品版本组织当前迭代，读 [版本路线图](../../../docs/RELEASE_ROADMAP.md)；纳入的功能各有目标版本，对外标题“FINNS <version>｜能力”。沿用稳定需求 ID 做内部追踪/去重，文档用修订号；目标版本、当前源码/部署版本和远程对象 ID 分开，规划不能提前改四处版本。
4. 把用户已明确的授权和修订写入决定记录，复用已有有效确认；不重复索要同一批准。建议、待决、已确认、已实现、已验收分别记录。
5. 需求评审通过时主动处理 G1→G2 的 Plane 同步检查点。提出管理差异与确认不等于调用远程工具；连接和每项写入继续遵守根 AGENTS 授权边界，不能因未获确认而默默忽略管理记录。

## 2. 读取本轮所需规范

- 推进开发阶段：读 [阶段门禁](references/stage-gates.md)。开始每阶段前检查输入证据；结束时列出产物、验证及下一阶段是否可进入。
- 概要设计定稿、引入外部服务/依赖/第三方额度，或设计被当作详设输入前：读 [设计评审](references/design-review.md)，做一轮设计合理性评审。
- 用户要求操作 Plane、给出工作项，或需求评审通过需提出同步确认：读 [Plane 同步协议](references/plane-sync.md)。没有对应指令时先在本地整理并询问，不自动连接/改写；普通问答不触发。
- 产生方案、原型、设计、测试、截图或交接：读 [AI 产物规则](references/artifacts.md)，使用 [记录模板](references/record-templates.md) 的相关部分。

新迭代目录 `docs/iterations/<target-version>/`，至少有当前计划与需规入口，文件名用英文。未采纳需求可用 ID 目录评估，排入当前迭代后明确产品版本，不能只留“下一版”。已有基线/历史保留原路径，转版时标明新权威入口，不并列维护冲突范围；不批量移动文件或承诺未经依据的日期。

## 3. 执行闭环

执行前、继续任务、阶段转换及交付前，必须按 [进度检查与 Plane 适配](references/progress-check.md) 运行只读检查器，核对每项功能的证据并给出当前阶段、缺口、AI 下一步及用户具体动作。FINNS 状态入口为 `docs/delivery-progress.json`。首次缺记录先从权威证据建立；未知不推定通过。通用适配只更换项目配置与证据，不复制本项目授权。

1. **登记**：写用户目标、范围、排除项、验收条件、未决事项、本轮操作边界及来源。
2. **评审**：先解决影响本轮范围的决定；形成可引用修订。新功能/明显交互变化先原型并取得用户对具体版本及范围的确认。
3. **管理同步与原型**：评审通过后主动列出 Plane 管理差异，取得所需指令/逐项确认后核对、写入并回读；无需变更或用户明确延期也要记录。检查点处理后制作产品原型，不把同步拖到收尾；等待期间可整理已授权资料，不提前声称原型制作已开始。
4. **设计**：原型及范围确认后明确概要、详设和接口/数据/错误/权限/测试映射。复用有效设计；小修复记录其适用理由，不机械扩写无关设计。概设定稿后先做一轮[设计合理性评审](references/design-review.md)（可豁免的情形和独立性要求见该文件），评审记录与概设一起作为 G3 证据，再进入详设与实施。
5. **实施与验证**：按获授权范围实现小闭环，检查实际退出码及可复现行为；按风险选择验证，不为凑流程重复收费请求或无关测试。
6. **归档与阶段同步**：产物关联验证和证据，更新索引、Unreleased 与交接；范围/管理状态变化时再提出对应 Plane 差异，不对无变化重复确认。失败/未验/待同步分别保留。
7. **交付**：说明实际完成、验证、未完成、运行边界和下一步。未实施的业务功能不得因文档/skill 完成而标为验收通过。

## 4. 不得跨越的边界

- 没有具体原型/范围确认，不开始对应的新业务功能开发；明确实施请求可以确认其中已展示的具体方案，但不能推断未展示的原型已获确认。
- 没有通过的行为证据，不标记相应验收完成；历史证据可引用，但注明日期、版本及本轮未复验。
- 没有发布授权、版本一致性与匹配风险的回退准备，不更新主站；四处版本只在实际发版时同步。
- 每个 Plane MCP 写操作均须本轮明确提出并逐次确认。调用本 skill 不自动获得远程写入权；“同步 Plane”不等于批准所有字段变化。
- “暂未获得写入确认”不是省略主动确认步骤的理由；G1 已通过与 Plane 已同步是两个事实。未核对/未执行/待回读不算已同步，也不把 G2“待制作”描述成原型已完成。
- 密钥、密码、Cookie、授权头、OAuth、未脱敏私人原文不进入过程归档或 Plane；不记录模型隐藏推理，只记录可审阅结论、取舍、决定及证据。
- 本 skill 约束 AI 的操作顺序，不能宣称已经形成 CI 强制门禁；缺少证据时必须如实停在对应阶段，并继续不依赖该决定的已授权工作。

## 5. 最低交接

使用模板记录：需求/Plane 映射、当前及目标版本、确认来源和修订、实际产物、验证结果与未验项、运行实例及数据触碰情况、未决事项、下一步进入条件。每轮检查所有本地链接，Plane 未同步或结果不明确时明确标记。

修改本 skill 后校验 frontmatter、引用与入口，并用至少一个适用请求、一个相邻不适用请求及关键失败情景走查。检查只能证明实际覆盖部分，不能冒称真实工具调用或完整流程自动验收。
