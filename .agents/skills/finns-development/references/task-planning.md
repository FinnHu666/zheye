# 任务识别、开发规划与隔离

用于 FINNS 的任务规划、接手、原型或业务开发。此文件维护任务与执行环境的判断，阶段批准继续以交付 skill 为准。普通问题直接答复；不要为应用本文件建立新项目、任务登记系统或后台服务。

## 1. 识别本轮请求

先依据当前会话、用户明确的工作项及本地权威资料确定任务。用户只说“继续”时沿用当前会话的任务与未完成目标，不能用交接文档最上方的另一项替换它。多个目标确实无法区分时，只询问影响执行的歧义，继续明确独立的工作。

| 请求模式 | 本轮可做的工作 | 不能据此推定的授权 |
| --- | --- | --- |
| 解释、诊断、查看状态 | 只读核对并答复 | 顺手改代码、更新任务状态或启动服务 |
| 记录、评审、制定开发计划 | 需求、验收定义、依赖及执行安排 | 制作原型、实现业务、建库或部署 |
| 制作、修改产品原型 | 已授权的模拟页面及匹配验证 | 真实服务端实现或对应功能验收通过 |
| 开发、实现、修复 | 在有效阶段证据覆盖的范围实施并验证 | 跳过未确认原型、Git提交/推送、部署或Plane写入 |
| 验收、发布、远程同步 | 用户指定的具体操作，遵循对应规范 | 将一个操作的授权扩展到其他操作 |
| 修改开发规范或skill | 本地流程文件、引用及行为边界验证 | 迁移现有任务、变更业务门禁或重建环境 |

同一句请求包含多个模式时，拆出各自范围与进入条件。授权持续有效，不重复询问已确认事项；缺少批准也不能靠请求中的“开发”二字补造阶段证据。

识别每项的稳定ID、目标版本、当前阶段、确认修订、已有实现/原型与本轮差异。读取 `docs/delivery-progress.json` 中该项及必要前置项，按交付进度协议核对证据。状态文件登记了多个任务不证明它们正在同时写文件；未知并发状态不得写成“已确认无人修改”。

## 2. 形成可执行计划

计划应说明：本轮可交付结果、影响文件/接口、前置条件、任务依赖、允许并行的部分、验证及完成判据。不承诺没有依据的日期或完成率。

区分三类依赖：

- **产品规则**：已经批准的规则直接复用；仍待决的差异单列，不重复要求批准既定规则。
- **接口/数据契约**：公共接口、权限或状态模型未确定时，先协调契约；不让不同任务各自实现冲突版本。已获授权的独立分析或模拟原型可先做。
- **写入/运行资源**：同文件、端口、测试库、构建输出或部署实例的占用，需要隔离或明确的串行安排。

不要把“依赖另一个功能”扩大成必须等待整项发布；列明真正需要的规则、契约或验证结果。每项仍独立满足自己的阶段条件。

## 3. 写入前核对实际工作区

先检查当前仓库根、分支、HEAD、`git status --short`、`git worktree list --porcelain` 及本轮拟改文件。将未提交改动区分为本项已知、他项已知、归属未知；已有改动不是可以回退的基线。

结合用户说明、当前会话、交接和可用的任务状态判断是否有其他写入者；有工具时可只读查看其他会话的工作目录，不擅自发消息、停止任务或派生代理。没有这些工具时按已知信息判断，不声称完成了其他客户端的盘点。

按需要核对服务端口、启动来源、输出路径和测试数据库。不要打印可能含凭据的完整环境变量或进程参数。端口占用只能证明有监听，不能证明服务已加载本轮代码。

| 实际情况 | 执行方式 |
| --- | --- |
| 只读答复 | 直接核对，不创建工作树或修改文件 |
| 纯需求、计划或流程文档；写入范围可控 | 可复用现有目录；公共文档按下节处理，不为文档机械建环境 |
| 单任务修复，无已知并行写入冲突，已有改动边界清楚 | 可复用合适工作区；不强制为每次小修复新建分支 |
| 多任务并行修改原型或业务代码 | 各任务独立工作树/分支与运行资源；或落实明确的串行写入安排后再改代码 |
| 未提交改动归属未知、同文件已有冲突、无法落实隔离或串行 | 只暂停受影响的写入，给出具体文件/资源及解决方案；继续独立且已授权的工作 |

“另开聊天”不隔离文件；在同一目录切换分支也不隔离文件。串行安排需有明确处理者及完成/交接条件，不能单凭另一个会话暂时空闲认定未来不会写入。

## 4. 多任务代码开发的隔离

在对应原型/实施阶段条件与本轮操作授权均满足时，执行可逆的常规隔离不必再次索要笼统批准。复用合适的既有工作树；需要新建时优先使用环境提供的托管worktree能力，无该能力时采用常规Git工作树。分支默认 `codex/<task>-<purpose>`，以实际名称为准；不自动提交、推送、合并或改主站。

显式选择核对过的起点，不能默认远程主分支就是当前产品版本。创建后核对新目录的仓库根与HEAD，后续命令及文件编辑实际指向该工作树；仅创建空目录、随后仍在原目录写代码不算完成隔离。资源按任务需要配置，纯浏览器原型不为凑隔离额外建数据库。

- **基线与已有改动**：先确定起点修订与依赖。新worktree不会自动带入当前目录的未提交文件，包括需规和原型。先列出确属本项且需要带入的差异；经边界核对后仅复制/应用这些文件或补丁并回读。归属不清时先展示具体清单、澄清必要项。禁止为了搬运方便整体stash、`reset --hard`、强制切分支、`git add .` 或搬走其他任务改动。用户未要求时，不借此迁移正在进行的任务。
- **端口与浏览器**：每个并行运行实例用经检查空闲的端口，按启动配置实际传入；不停止或复用别项服务冒充隔离。不同端口可以分开localStorage，但同主机Cookie通常跨端口共享，真实登录/会话验收还需独立浏览器配置或经过核对的测试会话配置。
- **数据**：使用各项独立的隔离测试库，遵守现有测试脚本的库名/主库保护；不新连业务主库，不自动删库。数据库实例可共用，但测试数据与迁移验证不能互相污染。Flyway编号在最终集成前统一分配与核对，独立库不能消除合并时的编号冲突。
- **构建与证据**：确认 `target`、前端输出、临时包、截图及日志解析到各自工作树/任务目录；不让不同构建同时清空同一个输出目录。工具或依赖可以按实际需要复用，禁止把整棵可写工作区/构建目录链接成共享位置后声称已隔离。
- **公共改动**：接口、公共组件、路由、状态模型和迁移由一个明确的集成步骤处理。各项只同步需要且已核对的依赖；不把整项合并或部署当作自动动作。集成后验证组合行为，单项测试不能证明组合通过。

## 5. 公共文档与进度记录

`docs/AI_HANDOFF.md`、`docs/NEXT_ITERATION_PLAN.md`、`docs/delivery-progress.json`、版本计划、ARTIFACTS及CHANGELOG均可能被多项同时修改。

- 变更前重读，按本项段落/JSON对象进行语义增量，保留其他任务的最新值；不从回合开始的旧副本整体覆盖。必须重写JSON序列化时，从写入前的最新文件构建目标并核对其他对象。
- 发现同一文件正在被另一任务写入时，明确由一个处理者串行整合；未完成协调前先保留本项补丁/记录，不争抢文件。重读和局部修改不是文件锁，不能宣称无竞争。
- 比较前后差异，区分自己修改与同期他项变化；禁止以“所有其他文件必须完全不变”的断言回退其他任务。
- 只有复核原批准语义仍有效时才更新受影响证据哈希；不能因文件变了就自动刷新全部证据。流程skill更新不改变业务任务门禁或完成状态。

## 6. 输出与交接

用一段短结论或按任务列行表达，不为简单任务强制生成新文件：

> 任务/目标版本；本轮模式与可推进阶段；依据及缺项；工作目录/分支与基础修订；隔离为已核实/计划/未隔离；共享依赖与串行范围；下一步及所需用户决定（无需时写无需操作）。

实际创建隔离环境后再记录路径、端口、库、输出及验证来源；不能用计划中的名称填成已运行。交接保留未提交差异去向、尚未集成的公共改动、独立/组合验证结果和未执行项。

此协议是AI的判断与执行约束，不是已部署的文件锁、CI阻断或自动调度器。若用户仅要求完善规范，应交付规范与验证，并清楚说明现有任务的实际隔离情况没有因此改变。
