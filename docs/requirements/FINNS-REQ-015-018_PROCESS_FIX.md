# 评审通过后的 Plane 同步节点修正

日期：2026-10-12。关联：FINNS-REQ-004 开发流程规范；REQ-015–018 本次案例。范围：修改项目 skill、流程入口及交接，分析刚才的操作；本轮不写入 Plane 或制作原型。

## 1. 实际发生了什么

用户确认需求评审通过后，AI 保存了修订 3 原文、更新 G1 通过状态，并编写 [产品原型任务书](FINNS-REQ-015-018_NEXT_STEP.md)。没有创建可点击原型、启动预览或改业务代码，也没有创建/更新本批次 Plane 工作项。

因此问题是**安排了原型下一步，却没有主动处理管理同步确认**，不是已经制作原型后才发现权限不足。此前只有用户分别确认的旧 P01/P02 写入，不能用于新需求。

## 2. 决策依据与遗漏

| 依据/行为 | 分析 |
| --- | --- |
| 用户要求“评审通过，现在更新下一步” | AI 按项目顺序将下一步安排为产品原型；这一阶段选择符合先原型再开发的要求 |
| AGENTS 要求 Plane 操作有对应用户指令、写入逐次确认 | 当前没有新工作项的具体写入确认，所以不直接写远程是正确的边界 |
| AI 把“没有写入授权”处理为“本轮不操作 Plane” | 遗漏：应主动准备本地待同步清单、提出核对/具体写入确认，而不是等用户再追问 |
| 原交付 skill 的同步步骤排在归档之后，并允许继续本地工作 | 缺少明确的 G1→G2 同步节点，容易把管理同步当作可选收尾，而优先推进阶段任务 |
| 原下一步任务书只标原型待制作，没有管理检查点 | 没有呈现“需求已通过，但管理记录待同步”；虽然未开始制作，也没说明先处理哪个确认 |

应修正的是主动确认责任与阶段连接，不能通过取消审批、把需求批准当作写入批准，或追溯声称已经同步来解决。

## 3. 新规则与责任

**需求评审通过 → AI 主动提出 Plane 同步清单/差异 → 对应授权及逐项确认 → 写入并回读（或核对无变化/用户明确延期）→ 实际产品原型制作。**

- 不等待用户重复问“有没有更新 Plane”；确认责任由 AI 主动推进。
- 尚无 Plane 指令时先整理本地清单并询问，未核实的项目/状态写明未核实；获得指令后再读取去重并完善具体差异，不自动连接。
- 需求通过和写入确认是两件事。每项远程操作仍独立确认，不沿用旧批次授权，不自动改 Done 或创建项目/Release。
- 用户明确说“先做原型，Plane 稍后补”构成延期决定，记录后继续；已同步无变化不重复问。没有回答不等于允许延期。
- 等待时可继续已授权的资料、任务书等工作；实际制作原型按检查点结果进入，不能静默跳过。
- 原型确认、范围变更、实施、验收/发布造成管理内容变化时，再处理实际差异；普通问答或无变更不机械增加审批。

权威规则在 [开发 skill](../../.agents/skills/finns-development/SKILL.md)、[交付 skill](../../.agents/skills/finns-delivery-workflow/SKILL.md) 及 [Plane 节点协议](../../.agents/skills/finns-delivery-workflow/references/plane-sync.md)。根 AGENTS 的连接/逐项写入边界与 MCP 审批配置保留。

## 5. 规则走查与验证范围

以下为本地规则干运行审阅，不是独立代理评测或真实 MCP 故障注入；所有真实远程操作次数为 0。

| 场景 | 新流程应采取的行动 | 走查结论 |
| --- | --- | --- |
| 评审通过但未给 Plane 指令 | 主动整理清单/询问；不自动连接、写入或默默进入制作 | 入口和协议明确覆盖 |
| 用户要求同步但未逐项确认 | 读取/去重，补齐具体差异，再逐项请求；批准前不写 | 根约定和第 0/2 节覆盖 |
| 已确认该具体写入 | 执行、回读、登记映射及阶段，再进入原型 | 不重复要求同一批准 |
| 远程核对无变化 | 记录无需变更，不创建重复项或索要无意义写入确认 | 作为检查点完成结果 |
| 用户明确暂缓或不使用 Plane | 记录来源和待补节点，继续已授权原型 | 不把暂缓写成同步完成 |
| MCP 失败，用户明确先原型 | 记录失败/待补，按授权继续；不假造远程成功 | 不一刀切阻断本地工作 |
| 用户没有回复 | 可以准备资料；不把沉默当作确认或延期 | 不默默跳过检查点 |
| 普通技术问答、小修复或无差异任务 | 不机械触发 G1→G2 检查点或远程调用 | 保持技能触发边界 |
