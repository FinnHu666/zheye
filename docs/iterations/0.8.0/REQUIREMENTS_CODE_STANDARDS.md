## 范围

| ID | 要求与边界 |
| --- | --- |
| STD-R01 | 建立 Java、Vue/JavaScript、SQL 规范，以及审查记录和严重度规则；被项目协作入口引用。格式规则、结构规则、迁移安全规则分别说明，不能声称格式化工具能核实全部业务安全。 |
| STD-R02 | 提供可独立执行、有明确退出码的检查命令，默认不修改文件、不启动应用、不连接数据库；钩子可选，不能成为唯一入口。工具与版本在设计阶段比较确认，依赖及安装位置遵守 D:/E: 或项目内约束。 |
| STD-R03 | 增量门禁基于可复现的比较基线，只阻断新增违规；旧违规用可追溯基线或显式豁免登记。详设明确新增、修改、重命名、删除和未提交文件的处理；基线缺失必须明确报错，不能默认为无问题。不能只因修改一个文件就强制整改该文件全部历史违规。 |
| STD-R04 | 明确作者维护的源码、测试和工具配置的纳入清单。历史 SQL 与 Java migration、被哈希登记的证据文档、第三方 vendor、构建产物、依赖和运行数据受保护。实施前记录迁移清单及哈希（当前 19 个 SQL 与 V7 Java migration，届时重新盘点）；不能只按 SQL 扩展名排除历史迁移。原型源码是否纳入留设计阶段明确。 |
| STD-R05 | 命名、包结构、分层、类大小等先成为可审阅规则；具体阈值及存量例外在设计中说明。存量结构问题登记供后续审查，本项不自动重构、拆类或改业务逻辑。 |
| STD-R06 | 新迁移遵守命名、缩进、约束/索引命名及头注释规则。头注释说明目的、关联文档、PostgreSQL 实测状态与证据，以及适用的前向修复/备份恢复/可逆回退策略；不强制每项提供 down SQL。“一个脚本一事”指一个逻辑变更。已执行迁移只追加不改写。 |
| STD-R07 | 记录 H2 JPA 与 PostgreSQL Flyway 的差异及一致性检查矩阵，明确字段、约束、索引与关键行为的验证方式。本项建立检查规则和适用入口，不扩张为开发完整跨库差异工具或整改全部既有差异。数据库验证须显式使用独立入口，仅连 loopback 的 finns_test_* / finns_restore_check_* 隔离库；H2 通过不能替代 PG 迁移验证。 |
| STD-R08 | 审查清单涵盖身份/权限/归属、会话、迁移、安全及验收映射；记录范围和基线、证据位置、严重度、事实/推测、未核实项、阻断条件、例外与复查结果。自动必过检查和人工审查分开。FINNS-26 负责首轮审查、安全依赖扫描与可复现基线，缺陷修复另定范围。 |

- 不改历史迁移、不批量改写旧证据、不做存量重构或业务缺陷修复、不新建远程 CI/分支保护。
- 需求评审可现在进行；正式路径配置、工具接入及实施依赖 FINNS-24 完成验收。按既有工程化基线决定，0.7.0 发布封板是后续工程实施的外部前置；本轮不执行发布。
