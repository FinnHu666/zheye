### 为什么拆成两个版本

0.7.0 集中修正创作前沟通、补基础统计和管理能力，可形成一个较小的独立闭环。0.8.0 引入新的配置模型、对象/评价数据、审核和独立复制，数据及权限风险更高，适合基于前一版管理能力单独验收。

把所有能力合并到一次发布，会让“简单首页统计”和“可变实体+评价后台”一起受阻，也难定位权限或数据回归。拆分保持原本已安排的多轮沟通仍在下一版，没有悄悄后移；新增榜单明确属于后续 0.8.0。

这不是最终工时/工期估算：原型、接口与数据设计完成后才能评估成本。若设计证明 0.7.0 管理范围过大，先缩小其已确认的简单目标，不用“管理”之名扩展整个平台；重大拆分变更再记录和评审。

## 3. 版本依赖与推进顺序

1. **版本需规**：按本次版本划分落文档，已评审方向沿用；具体参数显式待定。
2. **管理同步准备**：按版本汇总 Plane 组织方式及具体差异，当前仅规划，不执行已被用户改为只规划的 S15–S18 操作。
3. **0.7.0 原型/设计/实施**：同步检查点处理后，确认该版原型，概设/详设及授权实施；验收后按授权发布。
4. **0.8.0 原型与验证**：内容大纲及原型资料可提前准备；业务实现基于 0.7.0 约定的身份/访问基础，独立验证模块、评分和复制。
5. **0.8.0 发布**：以已验收基线推进；私人验证不等于开放公众数据或投稿，主站部署另核授权。

技术栈沿用 Java 17 / Spring Boot / Vue 3 / PostgreSQL，不因整理版本引入 Agent 框架或替换前端。

## 4. 版本及管理编号规则

- 对外标题使用“**FINNS 0.7.0｜某能力**”“**FINNS 0.8.0｜某能力**”；内部保留稳定需求 ID 和验收 ID，二者不是产品版本。
- 每个已纳入当前计划的功能必须有目标产品版本，不再只写“下一版/待排期”而缺少归属。0.7.0 内部映射：多轮沟通、REQ-015、REQ-016；0.8.0：REQ-017、REQ-018。
- 需规、计划分别使用“修订 1/2…”表示文档修改，不以“需规 1.0”暗示产品发布了 1.0。
- 规划版本不能提前写入 VERSION/pom/package/lock。实际发版时才同步四处版本及 CHANGELOG 发布记录；当前保持 0.6.0。
- 若发布后仅修复回归，可按实际内容规划相应补丁号，例如 0.7.1；本轮不凭空安排补丁需求或日期。
- Plane 的 Release/项目/工作项 ID 是远程管理标识，不代替产品版本。以后按版本容器或清楚的版本标题组织，创建、关联、改标题等各自须具体确认和回读。
